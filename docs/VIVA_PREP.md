### What is NOT Done with AI in VIONEX
1. **NO Image-Based Pest/Disease Diagnosis:** There is no computer vision model (no CNN, MobileNet, or Gemini Vision file upload). Pests and diseases are selected by agronomists from predefined drop-down taxonomies (`src/lib/utils.ts:71`).
2. **NO Autonomous Dosage Calculation:** AI is never permitted to dynamically prescribe chemical dosage volumes. All dosages originate from registered manufacturer label recommendations.
3. **NO Autonomous Agrochemical Safety Approvals:** Gemini is never tasked with deciding chemical tank compatibility or approving a spray schedule.
4. **NO Direct-to-Farmer Autonomous Execution:** Schedules generated from master blueprints are never pushed automatically to farmers; they require an agronomist or admin to explicitly configure plantation dates and click "Apply to Plot".

### How VIONEX Mitigates AI Output Risks
* **Strict JSON Schema Enforcement:** Using the `@google/genai` `Type` system (`Type.ARRAY`, `Type.OBJECT`, `Type.STRING`, `Type.NUMBER`), the model is constrained at the API level from returning markdown wrappers, conversational filler, or invalid keys.
* **15-Minute Rate-Limit Cooldown:** If `gemini-3.5-flash` encounters HTTP 429 or quota exhaustion, `lastGemini35ErrorTime` is set, dynamically shifting the sequence to prioritize `gemini-3.1-flash-lite` first (`server.ts:206-210`).
* **Deterministic Static Fallbacks:** For crop alerts and product searches, failures trigger deterministic hardcoded fallbacks so users are never left with broken UI states.
* **Human-in-the-Loop Review:** Master schedules, crop alerts, and product catalogs must be reviewed and saved by authenticated human administrators before being displayed to farmers.

### Worked Storage Estimation *(Labeled Clearly as an Estimate)*

The following estimates are calculated from TypeScript interface definitions in `src/types.ts` and actual seed JSON payloads:

1. **Farmer Document (`Farmer`):**
   * *Fields:* `id`, `name`, `mobile`, `pincode`, `country`, `state`, `district`, `taluka`, `village`, `villageCode`, `crops` (1–2 embedded plot objects), `dealer`, `paidStatus`, `access`, `loginStatus`, `createdAt`, `updatedAt`.
   * *Average Document Size:* **~600 bytes** (0.6 KB).
2. **Crop Plot (`FarmerCropEntry`):**
   * *Fields:* `id`, `plotName`, `crop`, `variety`, `season`, `area`, `plantationDate`.
   * *Average Size:* **~150 bytes** (embedded directly inside `farmer.crops[]`).
3. **Schedule Document (`Schedule`):**
   * *Fields:* `id`, `farmerId`, `farmerName`, `cropId`, `cropName`, `varietyName`, `day`, `dayNo`, `scheduleDate`, `method`, `otherMethod`, `stage`, `notes`, `done`, `doneAt`, `status`, `createdBy`, `selectedProducts` (array of 1–3 products with dosages).
   * *Average Document Size:* **~1,200 bytes** (1.2 KB).
4. **Product Document (`PreseededProduct` / Catalog):**
   * *Fields:* `id`, `brandName`, `marathiName`, `companyName`, `category`, `composition`, `compositionEnglish`, `modeOfAction`, `doseSpray`, `doseDrip`, `doseDrenching`, `doseBasal`, `targetCrops`, `targetPests`, `notes`, `status`.
   * *Average Document Size:* **~900 bytes** (0.9 KB).

#### How Many Documents Fit in 1 GiB ($1{,}073{,}741{,}824\text{ Bytes}$) of Free Firestore Storage?
* **Farmers only:** $\approx \mathbf{1{,}789{,}000\text{ farmers}}$
* **Schedules only:** $\approx \mathbf{894{,}000\text{ schedules}}$
* **Products only:** $\approx \mathbf{1{,}193{,}000\text{ products}}$
* **Realistic Mixed Production Dataset (1,000 farmers $\times$ 3 plots $\times$ 10 schedules/plot + 3,500 products):**
  * 1,000 farmers $\times$ 900 B = 0.9 MB
  * 30,000 schedules $\times$ 1.2 KB = 36.0 MB
  * 3,540 products $\times$ 0.9 KB = 3.2 MB
  * **Total Footprint:** $\approx \mathbf{40.1\text{ MB}}$ (utilizing less than **4%** of the 1 GiB free tier).

#### The 1 MiB Document Limit & Inline Base64 `photoUrl` Risk
* Firestore enforces a strict, unconfigurable maximum size limit of **1 MiB ($1{,}048{,}576\text{ bytes}$)** per individual document.
* *Critical Architecture Risk:* In `src/types.ts:82`, `Farmer` defines an optional `photoUrl?: string`. If an implementation encodes an uncompressed smartphone camera photo (typically 2–4 MB) as an inline base64 string directly into `photoUrl`, the document will immediately exceed the 1 MiB ceiling. Firestore will reject the write with `InvalidArgumentError` (`Document exceeds maximum size limit`).
* *Remediation:* Photos must be uploaded as binary blobs to Cloud Storage or Firebase Storage, storing only the lightweight HTTPS download URL string (~100 bytes) in Firestore.

#### App-Open Snapshot Listeners & Daily Read Quota Burn Rate
* In `src/lib/data-sync.ts:28-101`, `syncCollection()` attaches persistent `onSnapshot()` listeners to `farmers`, `schedules`, `products`, `dealers`, `consultants`, `alerts`, and `users`.
* Because these listeners execute collection-wide queries without server-side `limit()` or pagination on initial launch, **every document in the collection is read upon app open**.
* For a database containing 3,500 products, 500 farmers, and 1,000 schedules, a cold app launch consumes **5,000 document reads**.
* On the Firebase Spark free tier limit of **50,000 reads/day**, just **10 full cold launches** by staff members could completely exhaust the project's daily read quota.
* *Mitigation in Code:* The client mitigates this via `enableMultiTabIndexedDbPersistence` (`src/lib/firebase.ts:32`) and `getDocsSafe` (`src/lib/firebase.ts:174-232`), which intercepts queries and serves documents directly from local IndexedDB cache when data is unchanged.

#### Render Free-Tier Sleeping Behavior
* Render free-tier web services spin down (sleep) after **15 minutes of inactivity**.
* When a user triggers an API endpoint (`/api/villages`, `/api/advice`, `/api/search-products`) after the server has slept, the incoming request experiences a **cold-start delay of 50 to 90 seconds** while the container reboots.
* *Mitigation in Code:* Static fallback data in `server.ts` and client-side offline caches ensure the web/mobile app never crashes or hangs indefinitely while waiting for Render to wake up.

## SECTION 7 — Additional Examiner Topics

### 1. Build Pipeline & Deployment Workflow
* **Client Build:** Executed via `npm run build:client` (`vite build`). Vite compiles TypeScript and TSX, processes TailwindCSS v4 directives, bundles assets with code splitting, and outputs static production assets to `dist/`.
* **Server Build:** Executed via `esbuild server.ts --bundle --platform=node --format=cjs --packages=external --sourcemap --outfile=dist-server/server.cjs` (`package.json:8`). Esbuild pre-bundles the Express server into a single fast CommonJS executable for production deployment on Render.
* **Android Build:** Client assets from `dist/` are synced into the native Android WebView using `npx cap sync android`. Gradle then compiles native Java/Kotlin wrappers and packages `app-release.apk` (`android/app/build.gradle`).

### 2. Version Evolution from `CHANGELOG.md`
* **v1.2.1 (Security & Data Protection):** Introduced confirmation dialogs on product deletions, duplicate overwrite detection safeguards, and Service Worker cache eviction (`vionex-v9`).
* **v1.2.2 (UI Density & Access Control):** Redesigned Product Catalog into collapsible rows with smart multi-attribute search; strictly guarded edit/delete actions to admins (`isAdminOrAdminRole`); updated Android build to `versionCode: 3`.
* **v1.2.3 (Master Schedule Parity & Awaited Writes):** Replaced fire-and-forget patterns across 14 database operations with strict `await / try / catch` confirmed writes; launched "Apply to Plot" responsive modal; updated Android build to `versionCode: 4`.
* **v1.2.4 (Defensive Hardening & Crash Fixes):** Patched runtime exceptions on undefined phone numbers; hardened string normalization across product searches; protected `FarmerList.tsx` and `LocationMapping.tsx` against undefined taluka/village values; bumped Android build to `versionCode: 5`.

### 3. Firestore Document Modeling Strategy
* **Embedded Sub-objects vs. Root Collections:**
  * `farmer.crops[]` is embedded directly within the `Farmer` document to allow atomic updates of farm plots without paying extra read/write costs for separate subcollections.
  * `schedules`, `products`, `dealers`, `consultants`, and `activity-logs` are modeled as top-level root collections to support independent querying, filtering, and indexing across all farmers.
* **Soft Deletes vs. Hard Deletes:**
  * Products and farmers support soft-deletion flags (`isDeleted: true`) in code (`src/types.ts:91`, `src/components/ProductList.tsx:157`) to ensure historical schedules referencing deleted entities do not break.

### 4. Internationalization & Script Handling
* The codebase uses native UTF-8 Unicode matching for Devanagari script: `[\u0900-\u097F]`.
* Search algorithms in `src/lib/data-sync.ts:208` explicitly preserve Devanagari characters while stripping punctuation and non-alphanumeric noise, ensuring Marathi brand names and transliterations search cleanly.
